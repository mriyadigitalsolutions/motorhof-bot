# Спецификация: motorhof-bot, ядро + модуль photos

Источники: `2026-09-30-brief.md` (с «Дополнениями»), `PLAN.md` (версия 30.09.2026), `CLAUDE.md`.
Где спецификация уточняет PLAN.md, это помечено «уточнение PLAN»; нигде она ему не противоречит.

## Задача

Партнёры MOTORHOF снимают машины на iPhone, исходники лежат на общем диске Google Workspace
(DNG ProRAW по 30 МБ, HEIC, JPG). Чтобы выложить машину на willhaben / AutoScout24 / сайт,
кто-то садится за компьютер, конвертирует, уменьшает, переименовывает и вычищает геолокацию.
Это ручная работа, её легко сделать по-разному и легко забыть про GPS. Плюс старые ProRAW
занимают квоту диска, и никто не помнит, когда их можно удалять.

## Решение

Партнёр пишет боту в Telegram `/fotos MH_1022` с телефона. Через несколько минут в папке
машины на Drive появляется `Фотографии/На выгрузку/` с `MH_1022_01.jpg … MH_1022_NN.jpg`
(2000 px, качество 92, без GPS), а бот присылает отчёт со ссылкой на папку.
По `/fotos MH_1022 full` рядом появляются ещё полноразмерные `MH_1022_NN_full.jpg`.
Повторный запуск доделывает только новое. `/status` и `/last` показывают, что идёт и что было.
Через 60 дней после первой конвертации (или когда машину перенесли в «ПРОДАНО») бот
спрашивает, удалить ли исходные DNG; удаление — только после подтверждения администратора,
и в корзину Drive, а не навсегда.

Бот — это ядро плюс модули; photos — первый модуль, следующий добавляется папкой и одной строкой.
Всё в одном Docker-контейнере на Hetzner, поднимается одной командой и переживает перезагрузку.

## Решения по реализации

1. **Один процесс, asyncio.** aiogram 3 (long polling), в том же event loop — воркер очереди и
   планировщик. Конвертация тяжёлая и синхронная → `asyncio.to_thread`, чтобы бот отвечал на
   `/status` во время работы. Почему: PLAN §3, один контейнер, три пользователя.
2. **Очередь и журнал — SQLite** (`DB_PATH`). Таблицы ядра: `jobs` (id, module, kind, payload JSON,
   chat_id, telegram_id, user_name, status `queued|running|done|failed|interrupted`, progress_done,
   progress_total, created_at, started_at, finished_at), `runs` (PLAN §5 + user_name). Модули
   создают свои таблицы через `db.ensure_schema(sql)`. Статусы — конечный автомат
   `queued → running → done|failed`, `running → interrupted` только при старте процесса.
3. **Drive через rclone.**
   - `find_car`: 4 вызова `rclone lsjson <root>/<X_AUTO_Y> --dirs-only --max-depth 2`, отбор
     записей глубины 2, чьё имя начинается с `<КОД>_`. Результат: путь, ID, в какой из четырёх
     папок, год.
   - `list_files(dir)`: `rclone lsjson <dir> --files-only --max-depth 1 --hash --hash-type SHA256`
     (уточнение PLAN: хэш берётся у Drive, чтобы повторный запуск не качал 750 МБ).
   - `pull`: `rclone copyto` по одному файлу (только нужные, по списку); `push`: `rclone copyto`
     локального файла в `На выгрузку/<имя>` (перезапись того же имени, без дублей).
   - `mkdir`, `delete_to_trash` (`rclone deletefile --drive-use-trash=true`).
   - Все пути собираются из корня + сегментов; Drive-слой проверяет, что пишет/удаляет только в
     разрешённых поддеревьях (история 31).
   - Ненулевой код → `DriveError` с последними 5 строками stderr.
   - Бинарь rclone ставится в образ из официального релиза с фиксированной версией
     (в Debian-пакете слишком старый для SHA256 у Drive).
4. **Конвертация** — `convert.to_jpeg(src: Path, variant: Variant, dst: Path) -> ImageMeta`.
   DNG: rawpy с параметрами PLAN, EXIF читается Pillow из TIFF-структуры DNG. HEIC: pillow-heif,
   `ImageOps.exif_transpose`, ICC → sRGB через `ImageCms`. JPG: Pillow, то же. Ресайз LANCZOS
   до `max_side`, никогда не увеличивать. Сохранение: `quality`, `subsampling`, `icc_profile=sRGB`,
   `exif` по белому списку (история 18). Pillow пишет EXIF сам; `piexif` не нужен —
   **уточнение PLAN**: одна библиотека вместо двух, поведение то же.
5. **Манифест** `_manifest.json` — схема PLAN §4 плюс поля: `nn` (номер), `params`
   (отпечаток параметров варианта), `src_deleted`. Запись с `version: 1`. Правила:
   - ключ — sha256 исходника; один sha256 → один `nn` для всех вариантов;
   - новый sha256 → `nn = max(nn) + 1`, новые внутри запуска по дате;
   - sha256 из манифеста нет среди исходников и не `src_deleted` → `orphan: true`;
   - выход есть в манифесте, но нет файла в `На выгрузку` → пересоздать (нужен исходник);
   - `params` не совпали → пересоздать под тем же именем.
6. **Прогресс**: воркер обновляет `progress_done/total` в `jobs`; `/status` читает оттуда.
   Партнёру — не больше трёх сообщений на задачу.
7. **Планировщик** — часть очереди ядра: `queue.every_day("HH:MM", fn)`; время из
   `DAILY_CHECK_TIME` (по умолчанию 03:00), часовой пояс `TZ`. Удаление DNG — обычная задача
   очереди (`photos.delete_dng`), поэтому «одна задача за раз» соблюдается.
8. **Напоминания** — таблица модуля `photos_cars` (code, first_done_at, requested_by, chat_id,
   next_ask_at, asked_at, reminded, sold_asked_at, last_location `stock|sold`, state `idle|asked|pending_admin|done`, pending_request_id).
   `/fotos` этой машины после «тишины» возвращает state в `idle`. Callback-данные кнопок:
   `ph:del:<id>`, `ph:keep:<id>`, `ph:ok:<id>`, `ph:no:<id>` — id запроса, а не номер машины,
   чтобы старые кнопки распознавались как устаревшие.
9. **Доступ** — outer-middleware aiogram на message и callback_query: чужой ID → событие
   поглощается без ответа, строка в лог. Только `chat.type == private`.
10. **Настройки** — `core/settings.py`, dataclass из окружения; `.env.example` пополняется:
    `ADMIN_TELEGRAM_IDS`, `DNG_REMINDER_DAYS=60`, `DAILY_CHECK_TIME=03:00`, `TZ=Europe/Vienna`,
    `QUEUE_LIMIT=10`. Размеры/качество — только в `modules/photos/variants.yaml`.
11. **Docker**: `python:3.12-slim`, системные библиотеки для rawpy/pillow-heif приходят колёсами;
    `data/` и `rclone.conf` — bind mount; `restart: unless-stopped`; `env_file: .env`.
12. **Зависимости** (версии фиксируются в `requirements.txt`): aiogram 3.x, rawpy, pillow,
    pillow-heif, pyyaml; для тестов pytest, pytest-asyncio.

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| `core.settings` | конфигурация из окружения | `Settings` (dataclass), `load_settings() -> Settings` | разбор строк, значения по умолчанию |

| `core.db` | SQLite, схема ядра | `Database(path)`: `execute`, `fetchall`, `fetchone`, `ensure_schema(sql)`; `record_run_start(...) -> run_id`, `record_run_finish(run_id, ...)`, `last_runs(n)` | соединение, миграции, WAL |
| `core.queue` | задачи, воркер, расписание | `JobQueue(db)`: `register_kind(kind, handler)`, `enqueue(module, kind, payload, chat_id, telegram_id, user_name) -> EnqueueResult(job_id, position, duplicate_of)`, `status() -> QueueStatus`, `set_progress(job_id, done, total)`, `every_day(hhmm, fn)`, `start(notify)`, `recover_interrupted() -> list[Job]` | цикл воркера, таблица jobs, дедупликация по payload-ключу |
| `core.drive` | весь доступ к Drive | `Drive(remote, root, runner=subprocess_runner)`: `find_car(code) -> CarFolder`, `locate_all() -> dict[code, CarFolder]`, `list_files(path) -> list[RemoteFile]`, `pull(path, local)`, `push(local, path)`, `mkdir(path) -> folder_id`, `folder_id(path)`, `delete_to_trash(path)`, `folder_link(id) -> str`; исключения `CarNotFound`, `CarAmbiguous`, `DriveError` | вызовы rclone, разбор lsjson, проверка разрешённых путей |
| `bot.auth` | кто есть кто | `Access(settings)`: `is_partner(id)`, `is_admin(id)`, `admins()`; `AccessMiddleware` | разбор списков ID |
| `bot.router` | общие команды | `/start /help /status /last` | форматирование |
| `bot.main` | сборка процесса | точка входа `python -m bot.main` | порядок запуска |
| `modules.photos` | команда /fotos, цикл, напоминания | `register(router, queue)`; CLI `python -m modules.photos` | всё остальное |
| `modules.photos.job` | цикл одной машины | `run(code, variants, drive, workdir, progress) -> Report` | порядок шагов |
| `modules.photos.convert` | пиксели и EXIF | `to_jpeg(src, variant, dst) -> ImageMeta`, `read_meta(src) -> ImageMeta` | rawpy/pillow-heif/ICC |
| `modules.photos.manifest` | `_manifest.json` | `Manifest.load/dump`, `plan(sources, variants) -> Plan` | правила идемпотентности |

**Швы для тестов** (только эти):
1. `modules.photos.job.run` с `Drive`, у которого `runner` — фейковый rclone поверх локальной
   папки (`tests/fakes/fake_rclone.py`). Это главный шов: поиск, идемпотентность, отчёт, границы записи.
2. `modules.photos.convert.to_jpeg` на реальных фикстурах (пропуск, если файлов нет) и синтетике.
3. `core.queue.JobQueue` + `core.db.Database` на временной SQLite.
4. Обработчики бота — через функции-сервисы модуля, без сети Telegram (aiogram не поднимается).
