## Контекст

План (спецификация, «Решения по реализации» §11) предполагал, что `rclone.conf` монтируется в контейнер отдельным файлом (bind mount одного файла). В сборке (таск 07, строка манифеста D01) выяснилось: rclone сохраняет обновлённый OAuth-токен переименованием файла конфига, а смонтированный поодиночке файл переименовать нельзя — «Device or resource busy».

## Решение

В контейнер монтируется каталог `./rclone/` на запись; конфиг лежит в `rclone/rclone.conf` на сервере. Путь к конфигу указывает внутрь этого каталога.

## Почему

- Монтирование одного файла (исходный план) ломается на первом же обновлении токена — это доказано сборкой, не предположение.
- Монтирование файла только на чтение: rclone не сможет сохранить обновлённый токен, ошибки сохранения будут сыпаться в stderr, а он идёт в журнал и в сообщения партнёру.
- Запечь конфиг в образ: секрет попадает в образ, что нарушает R33 («никаких секретов в git и в логах») и R34 (конфиг вписывает пользователь сам после сборки).
- Передать remote через переменные окружения `RCLONE_CONFIG_*`: обновлённый токен некуда сохранить, OAuth-материал переезжает в `.env`.

## Последствия

- Контейнер имеет право записи в каталог с OAuth-секретом: скомпрометированный процесс может переписать конфиг.
- Файл обязан лежать именно в `rclone/rclone.conf`, а не в корне проекта; это надо помнить при деплое и переносе на другой сервер (README, «Открытые места»).
- Каталог `rclone/` должен быть исключён из git.
- Права на каталог должны позволять пользователю контейнера создавать и переименовывать файлы в нём, а не только писать в сам файл.
- Формулировка «`rclone.conf` — bind mount» в §11 спецификации описывает отвергнутый вариант; верна история 65.
